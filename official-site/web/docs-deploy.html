3 · Probe deploy — three modes

A · Nginx first-party recommended

# www vhost
location = /g5/g.js {
    proxy_pass https://pv.example.com/g.js;
    proxy_set_header Host pv.example.com;
    proxy_ssl_server_name on;
}
location /g5/ {
    proxy_pass https://gv.example.com/;
    proxy_set_header Host gv.example.com;
    proxy_ssl_server_name on;
    proxy_set_header Cookie $http_cookie;   # CRITICAL for cookie capture
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Gv5-Peer-Ip $remote_addr;
}
<script src="/g5/g.js" data-site-id="mysite" data-endpoint="/g5"
        data-inject-path="nginx" defer></script>

Same-origin ⇒ the visitor's Cookie header reaches the open request naturally. Never drop Cookie or X-Session-Id.

B · Cloudflare worker

export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    if (url.pathname.startsWith("/g5")) {
      const target = "https://gv.example.com" + url.pathname.slice(3) + url.search;
      const headers = new Headers(request.headers); // includes Cookie
      headers.set("X-Gv5-Peer-Ip", request.headers.get("CF-Connecting-IP") || "");
      return await fetch(target, { method: request.method, headers,
        body: request.method === "GET" ? undefined : request.body });
    }
    const res = await fetch(request);
    if (!res.headers.get("content-type")?.includes("text/html")) return res;
    const html = await res.text();
    const boot = '<script src="/g5/g.js" data-site-id="mysite" data-endpoint="/g5" data-inject-path="cf_worker" defer></script>';
    return new Response(html.replace("</head>", boot + "</head>"), res);
  },
};

Passing request.headers keeps the visitor's cookies intact. Avoid Cloudflare Under Attack on /g5 (challenge pages break open/ingest).

C · Site script / CDN embed

<script src="https://pv.example.com/g.js" data-site-id="mysite"
        data-endpoint="https://gv.example.com" data-inject-path="app" defer></script>

Cross-origin fetch does not send cookies by default. Reliable capture: (1) same-site path/subdomain, or (2) your backend opens the session server-side with the visitor's Cookie header and the page continues that session.

4 · Receive results — six-language SDK

Create a backend key in the site config (GR_SITE_RESULT_KEY). The SDK never relays probes; it only queries results.

LangPathCall
JSsdk/src/index.jsnew Gv7ResultClient({baseUrl, apiKey}) → waitForResult(...)

Contract:

GET {gv_base}/v1/session/{session_id}/result?projection=sdk
X-Gr-Sdk-Key: <site backend key>

{
  "ok": true, "schema_version": "product_public_v1",
  "session_id": "sess_...", "projection": "sdk",
  "sdk_projection": {
    "algo": "sdk_slim_projection_v1",
    "emit_identity": true,
    "cookie_fields": { "user_id": "u9", "plan_tier": "pro" }
  }
}

projection ∈ public | sdk | diagnostic (diagnostic = ops token only). Every client ships cookieFields/cookie_fields returning the allowlisted cookies or null.

5 · End-to-end smoke (curl)

OPEN=$(curl -fsS -X POST https://gv.example.com/v1/session/open \
  -H 'Content-Type: application/json' \
  -H 'Cookie: user_id=u9; plan_tier=pro; __oauth=skipped' \
  -d '{"site_id":"mysite","visitor_terminal_id":"vt_demo1","meta":{"inject_path":"nginx"}}')
SID=$(printf '%s' "$OPEN" | jq -r .session_id)

curl -fsS -X POST "https://gv.example.com/v1/session/$SID/analyze" \
  -H "X-Gr-Sdk-Key: $GR_SITE_RESULT_KEY" \
  -H 'Content-Type: application/json' -d '{}' >/dev/null

curl -fsS "https://gv.example.com/v1/session/$SID/result?projection=sdk" \
  -H "X-Gr-Sdk-Key: $GR_SITE_RESULT_KEY" \
  | jq '.sdk_projection.cookie_fields'
# → {"user_id":"u9","plan_tier":"pro"}  (oauth cookie NOT captured: not allowlisted)

Health: GET {pv}/v1/health, GET {gv}/v1/health, panel /api/me (version), /api/probe-health, /api/lb/status.

6 · Security notes

  • Allowlisted cookie values are the site owner's own data; keep the allowlist minimal and treat values as business identifiers.
  • Site SDK keys are read-only, site-bound, never in the browser.
  • Diagnostic projection / evidence / analyses require ops scopes.
  • The sensitive-name blocklist is a hard server-side stop on top of the owner allowlist.
